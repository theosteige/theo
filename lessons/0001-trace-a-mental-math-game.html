Trace one game through the whole website

Your tangible win: after this lesson, you can point to the exact system and file responsible for every stage between clicking “Start” and seeing a saved score in Game History.

Start with one sentence: the browser plays the game, the Worker decides whether a record may be saved, and D1 remembers it.

The three-system mental model

GitHub Pages
delivers files→Browser JavaScript
runs game→Cloudflare Worker
guards API→Cloudflare D1
stores rows

GitHub Pages is a file host here; it does not execute the game or write records. public/mental-math.js executes in the visitor's browser. Its cross-origin fetch() calls go to the Worker, whose standard entry point is fetch(request, env). The DB binding on env gives that Worker access to D1.

Retrieval 1: Who sends the HTML?

A timed game, step by step

  1. The browser reads settings.

    public/mental-math.js validates the operation checkboxes, numeric ranges, and selected duration. Nothing has reached Cloudflare yet.

  2. The browser generates and times questions.

    Each correct answer increments an in-memory score. The response timer starts when the question appears and stops when the correct value is entered, so time spent making mistakes is naturally included.

  3. The timer ends and the browser posts JSON.

    The payload contains score, duration, settings, and compact answer attempts. The password field becomes an HTTPS Bearer authorization header.

  4. The Worker distrusts the browser.

    workers/scores.js compares the submitted key with the Cloudflare WRITE_KEY secret and independently validates every score, setting, duration, operand, operator, and response time.

  5. D1 stores one game and its attempts.

    The Worker batches an insert into scores with an optional insert into attempts. Commutative operands are sorted first, so 5 + 2 and 2 + 5 share one analytical identity.

  6. The public UI reads it back.

    GET /scores requires no key. Game History shows every timed game; Progress filters to the exact 120-second default configuration; the yearly calendar adds each game's duration to its Pacific-time date.

Retrieval 2: Where does the entered key live?

Practice mode takes a shorter path

What is saved

Clicking “Exit practice” measures elapsed seconds and posts them to /practice-time. D1 increments the lifetime counter and creates a dated practice_sessions row for the calendar.

What is not saved

No practice score or per-question attempt is stored. No key means no write. Closing or reloading the tab skips the exit handler, so that session is also not stored.

Retrieval 3: You exit practice without a key. What happens?

The deployment seam

The source HTML contains only data-score-api. On a push to main, the GitHub Actions workflow substitutes the configured SCORE_API_URL into the uploaded copy and deploys public/. The repository file stays environment-neutral.

The Worker is a separate release. If a change needs a new table or column, deploy in dependency order:

D1 migration→Worker code→Static page

That order ensures the new Worker never queries a schema that does not exist, and the new page never calls an API that has not arrived.

Checkpoint: predict where three changes belong before revealing

Change the Piano paragraph: public/piano/index.html; Pages deployment only.

Allow a new timed duration: mental-math HTML/JS and Worker validation; Worker first, then Pages.

Store a new game field: numbered SQL migration, Worker read/write logic, then browser rendering; D1 → Worker → Pages.

Keep this, not every detail

If you remember only one diagnostic question, use: “Is this a file-delivery problem, a browser-behavior problem, an API-policy problem, or a stored-data problem?” That usually tells you whether to open public/, public/*.js, workers/scores.js, or migrations/.
