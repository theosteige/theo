Theo's website, end to end

A field guide to what runs where, which files matter, how mental-math records move, and how to deploy without mixing up the two production systems.

The whole architecture: GitHub Pages serves the files in public/. Browser JavaScript calls a Cloudflare Worker for mental-math records. The Worker reads and writes Cloudflare D1. There is no framework, application server, package manifest, or static-site build.

What “lightweight” means here

Code is small

No React, Astro, package bundle, client router, component runtime, analytics library, or CSS framework ships to visitors. Shared JavaScript is about 100 bytes; the specialized mental-math script is about 12 KB.

Media is intentionally large

The tracked repository is roughly 87.5 MB, almost all original-quality images, audio, video, and the résumé. The code and HTML together are a tiny fraction of that total.

The Piano page is especially economical: three links retarget one lazy-loaded, privacy-enhanced YouTube iframe. The Design page keeps media as ordinary DOM children; a 52-line script recalculates the binary mosaic whenever a child is added and opens the selected original in a native <dialog>.

Mental-math browser behavior

  1. Settings become a plain object.

    The checked operations, numeric ranges, and duration are validated in the browser. Practice is represented as a null duration; timed games use 30, 60, 120, 300, or 600 seconds.

  2. Questions are generated locally.

    Addition and multiplication choose operands directly. Subtraction starts with two positive values and displays their sum minus one value, guaranteeing a non-negative integer result. Division reverses a multiplication, guaranteeing an integer answer.

  3. Only correct completions advance.

    A question's timer starts at generation. Wrong input is not stored separately, but its delay is included because the timer stops only when the correct answer arrives.

  4. Timed and practice games end differently.

    A timed game posts its score, settings, duration, and correct-answer attempts when the countdown ends. Practice runs until “Exit practice” and posts only elapsed seconds. Closing or reloading a practice session does not save it.

  5. The UI renders public records.

    Anyone can fetch game history and practice totals. The progress line filters to 120-second games with every default operation and range. The history list shows every timed game. The activity calendar includes all timed-game minutes plus dated practice sessions.

The calendar uses the current year in America/Los_Angeles. The pre-session practice total of 1,997 seconds is included in the 2026 cumulative heading but cannot be assigned to a historical day, so it does not color a cell. Future practice exits produce dated rows and therefore appear on their day.

API contract and trust boundary

MethodRouteJournal key?Behavior
GET/scoresNoReturns every valid timed-game score, timestamp, duration, and settings object.
POST/scoresYesValidates the payload, saves the score, and batch-inserts canonical answer attempts.
GET/practice-timeNoReturns the cumulative total, undated legacy amount/year, and dated sessions.
POST/practice-timeYesAtomically increments the total and inserts a dated practice session.

The journal key is sent as an HTTPS Authorization: Bearer … header. Its expected value is the encrypted Cloudflare secret WRITE_KEY, never a repository file. The browser does not put the entered key in cookies or local storage: it remains in the password field for the current page lifetime and disappears on reload or navigation.

CORS is not the password. The Worker returns browser-readable responses only to theosteiger.com and configured localhost origins, but non-browser requests can omit Origin. That is intentional because reads are public. Every write is independently protected by the journal key.

D1 schema

TableStored dataImportant detail
scoresScore, ISO timestamp, duration, JSON settingsOne row per saved timed game.
attemptsGame timestamp, operator, canonical operands, response millisecondsAddition and multiplication operands are sorted, making 5 + 2 and 2 + 5 the same question. Subtraction and division keep their order.
practiceOne cumulative total_seconds valuePreserves the original total across the dated-session migration.
practice_sessionsISO timestamp and elapsed secondsNew practice exits can be placed on the activity calendar.

Attempts are collected but are not exposed by a public API or displayed on the site. Analyze them through D1, for example:

SELECT operation, left_operand, right_operand,
       COUNT(*) AS answers,
       ROUND(AVG(response_ms) / 1000.0, 2) AS average_seconds
FROM attempts
GROUP BY operation, left_operand, right_operand
ORDER BY average_seconds DESC;

Why the deployed HTML differs from the repository

The repository intentionally contains a bare data-score-api attribute. During the Pages workflow, one sed command injects the repository's SCORE_API_URL variable into the artifact. This keeps the production URL out of page-maintenance work while avoiding a build system. A plain local static server therefore runs the game but reports that syncing is unconfigured unless the preview injects a local or production API URL.

Safe release checklist

  1. Preview and validate.

    Serve public/, exercise the changed page, run JavaScript syntax checks, and inspect git diff --check.

  2. Apply schema first, if any.

    Run npx wrangler d1 migrations apply mental-math --remote, then list migrations and perform a read-only schema check.

  3. Deploy the Worker second, if changed.

    Run npx wrangler deploy, then call only the public GET routes to verify response shape. Never create a production test score.

  4. Push the static release last.

    Commit and push main. The Deploy workflow substitutes the API URL, uploads public/, and publishes the artifact to GitHub Pages.

  5. Verify the actual public URLs.

    Check the exact commit's workflow, cache-bust the page and assets, confirm removed text is absent, and confirm the Worker still returns preserved data.

Current sharp edges

  • The static site and Worker are separate deployments, so a breaking API change must be sequenced carefully.
  • There is no automated test suite in the repository; validation is currently targeted syntax, API, database, and browser QA.
  • Attempt data has no export or analysis interface yet.
  • Practice time is saved only when “Exit practice” runs successfully with the key present.
  • The public GET routes deliberately use Cache-Control: no-store, favoring fresh personal records over caching.
  • The latest Pages run succeeds, but GitHub warns that several pinned action versions still target its deprecated Node 20 action runtime. This is maintenance debt, not a current deployment failure.
